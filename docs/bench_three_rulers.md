# 三把尺子：26 秒、237 QPS 和 3 条失联连接

> 一次压测，我测出三种"系统有病"。最后发现，两次病在尺子上。
> 项目：teyvat-guild（FastAPI + MySQL 8.4 + Redis + SQLAlchemy 2.x 异步）
> 机器：i7-14650HX / 16 核 24 线程 / Windows 11 / Python 3.13
> 日期：2026-11-17

---

## 0. 起因

结算闭环刚收口，198 个测试全绿。我想测点压测数据写进简历——"抢单接口扛得住 N 并发"这种话，没有数字撑不住。

项目里有个现成的 `bench_accept_full.py`，S1~S4 四段：串行基线、同单争用、无争用吞吐、大厅读吞吐。我以为跑一遍就能拿到数字。

结果第一个数字出来是 **26.5 秒**。

---

## 1. 第一把尺子：单请求 26.5 秒

S1 是串行基线：一个请求发出去，等它回来，再发下一个。设计它的意义就是——**串行都慢，就说明问题在业务链路本身，跟并发一点关系没有**。

```
[S1] 串行基线（10 次单请求）
    p50=26483.3ms p95=27601.0ms p99=27601.0ms
```

26.5 秒一个请求。紧接着 S2 更奇怪：同单 20 并发，1 个成功、19 个返回 409，但**冲突请求的 p50 也是 26.9 秒**——冲突方明明不该碰任何缓存。

### 分层计时，把 26 秒切成两截

猜没有用，直接量：

```python
# 数据库
async with AsyncSessionLocal() as db:
    await db.execute(text('select 1'))
# Redis
await cache_get_json('teyvat:hall:probe')
```

```
DB  select1: 3.0 ms
Redis get : 26600.0 ms   ← 找到了
```

MySQL 3 毫秒，Redis 26.6 秒。

### 第一层：容器端口"配置有、运行时无"

`docker ps` 显示 redis 容器活着：

```
teyvat-redis   Up 45 minutes   6379/tcp
```

注意 **`6379/tcp`** 前面没有 `0.0.0.0:6379->`。而 compose 文件里明明写着 `- "6379:6379"`。

再看容器的运行时状态：

```bash
docker inspect teyvat-redis --format 'PortBindings={{json .HostConfig.PortBindings}} Ports={{json .NetworkSettings.Ports}}'
```

```
PortBindings={"6379/tcp":[{"HostIp":"","HostPort":"6379"}]}
Ports={"6379/tcp":[]}
```

**配置要绑，运行时绑了个空数组。** 容器创建那一刻宿主 6379 被别的容器占着，Docker 没绑定成功，但容器照样 Up 着、日志里一个字都不提。宿主机 `netstat :6379` 空无一人。

修法：

```bash
docker compose -f docker-compose.dev.yml rm -sf redis
docker compose -f docker-compose.dev.yml up -d redis
```

> 排查这类问题，别只看 compose 文件对不对，要看 `NetworkSettings.Ports` 到底是不是空数组。配置是意图，运行时状态才是事实。

### 第二层：写了降级代码 ≠ 有降级行为

端口修好之前，我先改了代码。因为 `cache.py` 里明明写了降级：

```python
async def cache_get_json(key: str):
    try:
        raw = await get_redis().get(key)
        return json.loads(raw) if raw else None
    except Exception:
        return None      # ← Redis 挂了就当 miss，退回直查库
```

注释写着"Redis 挂了业务照跑，只是退回直查库"。**实测：Redis 挂了，业务挂 26 秒。**

原因在客户端建连参数。我以为是缺超时，于是只加了超时：

```python
socket_connect_timeout=0.5
socket_timeout=0.5
```

实测：**10 秒**。还是不对。

因为 `redis-py` 8.x 默认带着指数退避重试，一次连不上会自己重试多轮，超时参数管的是"单次连接"，管不住"重试几轮"。

三个参数缺一不可：

```python
from redis.backoff import NoBackoff
from redis.retry import Retry

aioredis.Redis(
    host=settings.redis_host,
    port=settings.redis_port,
    decode_responses=True,
    socket_connect_timeout=0.5,      # 单次连接别等太久
    socket_timeout=0.5,              # 单次读写别等太久
    retry=Retry(NoBackoff(), 0),     # 不重试
    retry_on_error=[],               # 出错也不重试
)
```

实测对比（同一个连不上的端口）：

| 配置 | 失败耗时 |
|---|---|
| 什么都不加（默认） | 26 600 ms |
| 只加 `socket_connect_timeout` + `socket_timeout` | 10 000 ms |
| 再加 `Retry(NoBackoff(), 0)` + `retry_on_error=[]` | **500 ms** |

500ms 还是不够快，但已经是"能降级"的级别了。

### 为什么这一个点能拖垮整场压测

`cache_delete_prefix()` 在**事务内**执行——也就是行锁还攥在手里的那段时间。所以一次 26 秒的缓存调用，等于 26 秒的持锁时间：

```
Redis 连不上 → 单次缓存操作 26s
    ↓
accept 成功路径在事务内删缓存 → 行锁被攥 26s
    ↓
同单另外 19 个请求全在等这把行锁 → 所以 409 也要 26.9s
    ↓
S3 的 30 单并行 → 全部排在锁后面 → QPS=1
```

**S1 的 26 秒不是性能问题，是故障没有被快速降级。** 修完之后同一个 S1 变成 16.8ms，快了 1500 倍——但这 1500 倍不是优化来的，是把一个本不该存在的等待去掉了。

## 2. 第二把尺子：237 QPS

Redis 通了，数字正常了：

```
[S1] p50=16.8ms
[S2] 成功 p50=45.0ms | 冲突 p50=71.2ms
[S3] QPS=158  p50=132.3ms
[S4] QPS=239  冷=7.1ms 热 p50=50.2ms
```

于是我加多进程，`--workers 4`，再跑：

```
[S3] QPS=164      （158 → 164）
[S4] QPS=237      （239 → 237）
```

**四个进程，QPS 一动不动。** 这时候最容易得出的结论是"瓶颈在数据库"或"瓶颈在锁"，我开始往那个方向查。

### 用并发梯子做判别

真正的判别不是猜瓶颈，是**改变并发，看 QPS 怎么动**：

| 客户端并发 | QPS | p50 | 客户端 CPU |
|---|---|---|---|
| 1 | 250 | 3.8ms | 78% |
| 10 | 222 | 30.6ms | **100%** |
| 20 | 208 | 59.5ms | 97% |
| 50 | **190** | 139.8ms | 99% |

**并发越高，QPS 越低。**

服务端饱和时 QPS 会走平，不会下降。下降意味着请求在排队——而排队的不是服务端，是客户端自己的 CPU。表里最后一列写着：一个 Python 进程跑 httpx，在 250 QPS 就把一个核吃满了（URL 解析、头字典、Response 对象、JSON 解码，全是这个进程干的）。

**我一直在测我自己写的压测脚本。**

### 换成裸 socket

同样一个接口，换成预构造字节流 + keep-alive，不构造任何 Response 对象：

```python
REQ = ("GET /commissions/hall?page=1&page_size=20 HTTP/1.1\r\n"
       "Host: 127.0.0.1:8000\r\nConnection: keep-alive\r\n\r\n").encode()

async def worker(n, lat):
    reader, writer = await asyncio.open_connection(HOST, PORT)
    for _ in range(n):
        t0 = time.perf_counter()
        writer.write(REQ)
        await writer.drain()
        head = await reader.readuntil(b"\r\n\r\n")   # 读头
        # 按 content-length 读体
        lat.append((time.perf_counter() - t0) * 1000)
```

| 客户端 | 连接数 | QPS | p50 | 客户端 CPU |
|---|---|---|---|---|
| httpx | 20 | 237 | 51.0ms | ~100% |
| 裸 socket | 10 | **2453** | **3.1ms** | 12% |

**差 10 倍。**

这里我犯过一个错，值得单独记一笔：在这次测量之前，我用 `4.1ms × 300 请求 = 1230ms ≈ 实测 1250ms` 推过"串行度 98%，所以是服务端单进程事件循环卡住"。算术没错，但那 4.1ms 里有 3ms 是 httpx 自己的开销——**我把客户端的账单记到了服务端头上**。

`QPS` 这个数字永远属于整条链路里最慢的那一环。报数字的时候如果不报尺子，等于没报。

## 3. 第三把尺子：3 条失联连接

这是整轮里唯一一个真问题。

两个 worker 配置对着测，10 条连接都正常。加到 20 条连接时：

```
连接= 20  请求= 85  QPS= 17  p50= 7.51ms  超时连接=3
```

100 个请求只完成 85 个，**3 条连接在 5 秒内一个字节都没收到**。同一时刻单连接只要 4.49ms，服务端进程也活着。

### "连接已建立"其实是谁建立的

这一点想清楚了，整个现象就通了：

> **TCP 三次握手是内核完成的，不是应用完成的。**

握手成功后，内核把连接放进监听 socket 的 **accept 队列**（backlog），等某个进程调用 `accept()` 把它取走。客户端 `connect()` 返回成功，只说明内核接下了这个连接——如果四个 worker 里没有一个来 accept，这条连接就永远躺在队列里。

所以"服务端接了连接却不回"更准确的说法是：**内核把它接进了队列，应用层没人来取**。

这也解释了两件看起来矛盾的现象：

- 客户端看到的是连接成功（内核握手完成）
- 服务端"没崩溃"（进程都活着，单连接照常 2ms）

### Windows 上为什么容易这样

Linux 上多进程共享监听 socket 是条走了几十年的路：`fork()` 之后子进程各自持有一份 fd，内核保证"一个连接只唤醒一个进程来 accept"（早期靠 accept mutex，后来有 `EPOLLEXCLUSIVE` 和各进程独立的 accept 队列）。

Windows 没有 `SO_REUSEPORT`。uvicorn 的 `--workers` 在 Windows 上走 `multiprocessing.spawn`，做法是把**同一个 socket 句柄复制**给 4 个子进程，每个子进程跑一个 Proactor 事件循环，各自往这个共享句柄上投递 `AcceptEx()`。多个进程同时在一个句柄上等 IO 完成，完成通知落到谁身上、会不会漏，没有可靠保证。

**我不敢断定内核里具体漏在哪一步**（那需要抓 ETW 事件），但因果关系可以钉死——用一个判别实验。

### 判别实验：只去掉一个变量

| 配置 | 20 连接 | 结果 |
|---|---|---|
| `--workers 4` | 100 请求 | 完成 85，3 条连接永久失联 |
| 单 worker | 100 请求 | **100/100，0 超时**，1078 QPS / p50 14.84ms |

同一个脚本、同一台机器、同一个接口、同一个数据库，唯一差别是 `--workers`。

**问题在启动参数上，不在业务代码、不在 Redis、不在 MySQL。**

### 结论

- 本地开发永远单 worker（`--workers` 也不能和 `--reload` 同时用，正好统一）；
- 多进程只在 Linux / 容器里测，那边的 socket 继承机制是另一套；
- **Windows 上测出来的多进程增益不能写进任何报告。**

## 4. 顺手推翻了自己三个月前写的结论

翻旧文档 `bench_accept.md`，看到第 29 行：

> "**CAS 下失败者立即返回，无排队**（详见第 7 节）"

今天的数据打脸：

```
[S2] 5 轮 × 20 并发抢同一单
  第1轮 {200: 1, 409: 19}   状态=进行中   冒险家=391
  ...
  成功 p50=45.0ms | 冲突 p50=71.2ms p99=104.0ms
```

冲突方比成功方**慢 26ms**。如果真"无排队"，两边应该一样快。

原因很简单被我写漏了：CAS 是 `UPDATE ... WHERE status='待接单'`，**UPDATE 本身也要拿行锁**。失败者不用显式 `SELECT FOR UPDATE` 排队，但它们的 UPDATE 语句仍要在锁队列里排一次，拿到锁、判断 `rowcount == 0`、再回滚。19 个人排队，每次锁交接 ≈1.4ms，正好 26ms。

真正省掉的不是"排队"，是"排队之后还要跑一遍完整业务逻辑"——`SELECT FOR UPDATE` 版本的失败者排队醒来后，还要走一遍校验、改状态、写日志、删缓存；CAS 版本的失败者醒来只需一句 `rowcount == 0` 就返回。

所以那句话应该改写成：

> CAS 把失败路径从"排队 + 完整业务逻辑"压缩成"排队 + 一次条件判断"。

**写结论时把限定条件一起写下来，三个月后你才分得清它是被推翻了，还是被误读了。**

## 5. 最终留下来的数字

| 指标 | 数值 | 条件 |
|---|---|---|
| 大厅读吞吐（单进程） | **1355 QPS / p50 6.56ms** | 10 并发、缓存热态 |
| 同上，20 并发 | 1078 QPS / p50 14.84ms | 已饱和 |
| 缓存收益 | 冷 16ms → 热 3.5ms（**4.6×**） | 同为单发，大厅 20 条挂单 |
| 抢单正确性 | 每轮 1×200 + 19×409 | 5 轮 × 20 并发抢同一单，零重复接单 |
| 抢单延迟 | 成功 45ms / 冲突 p50 71ms | 含 19 人排队等行锁 |

"单进程 ≈1350 QPS"这个数是交叉验证过的：10 连接测出 1355；20 连接测出 p50 14.84ms，`20 ÷ 0.01484 ≈ 1348`。两条完全不同的路径算出同一个上限，这才是可信数据。

顺带一个反例：S4 早先报过"冷 50ms → 热 4.1ms，12 倍"。那个 12 倍是假的——第一次请求在付进程冷启动的钱（模块导入、首个连接建立）。进程热了之后冷查询是 16ms，加速比 4.6 倍。**冷热对比必须在同条件下做，否则你测的是启动开销。**

## 6. 方法论清单

1. **先验尺子，再测系统。** 客户端 CPU 单核 100% 时，所有 QPS 数字作废。
2. **并发梯子**：并发涨而 QPS 跌 → 尺子到顶；QPS 走平 → 服务端真饱和。
3. **判别实验**：怀疑 A 导致 B，就去掉 A 再跑一次。不要靠推理，靠对照。
4. **分层计时**：DB 一次、Redis 一次、HTTP 一次，各自计时，别猜。
5. **冷热同条件**：都单发，或都同并发。混着测出来的倍数没有意义。
6. **串行能通，才允许并发。** 串行就挂，一定是业务链路问题，跟并发无关。
7. **会挂死的脚本等于没有脚本。** 压测脚本必须带单请求超时 + 总闸，遇到不回的服务端要计数跳过而不是等人 Ctrl+C。
8. **结论带条件。** 写"无排队"要写成"排队 + 一次条件判断"，否则三个月后连自己都分不清是错了还是被误读了。

## 7. 复现

```bash
# 服务端（本地开发用单 worker）
uvicorn app.main:app --port 8000

# 全链路压测：S1 串行 / S2 争用 / S3 吞吐 / S4 缓存 + S4b 裸 socket
python -m app.bench_accept_full

# 大厅读上限：裸 socket，用来给 worker 数做 A/B
python -m app.bench_hall_raw 400 10
```

压测脚本里两处刻意的设计：

- **S4b 用裸 socket 另起一段**：同一份报告里同时给"应用侧 QPS"和"协议侧 QPS"，被客户端骗过一次就不会再被骗第二次；
- **每次跑都往库里写真实订单和用户**：不重置、不造数、不 mock，测的是真实行为——数据脏了手动清，别让脚本替你把环境擦干净，那样你永远不知道自己测的是什么。

## 8. 这一轮真正学到的东西

数字会过期，机器会换，QPS 明天就不作数了。留下来的只有三件事：

1. **降级代码写了，不等于降级行为存在。** 必须在真实故障下跑一遍，否则你写的是注释，不是代码。
2. **测量工具本身也要被测。** 尺子饱和时的读数，比没有读数更危险——因为它看起来像个结论。
3. **"我以为"和"我测了"之间的距离，正好是一篇博客的长度。**
